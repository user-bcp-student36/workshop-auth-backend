# HU-01 - Token firmado con expiracion y claims minimos

## Origen

Filas de [HALLAZGOS.md](HALLAZGOS.md) en estado "Pendiente" relacionadas con el token. Todas las rutas de código son relativas a `src/main/java/com/bcp/workshop/auth/`.

| Id | Hallazgo | Evidencia (archivo:linea) |
|---|---|---|
| H-02 | Token Base64 con secreto embebido | `LegacyTokenUtil.java:8,13-15`; `AuthResource.java:39` |
| H-04 | Secreto hardcodeado (solo la parte del secreto; el CORS queda fuera de esta HU) | `LegacyTokenUtil.java:8` |
| H-07 | Literal `3600` duplicado y creación del token dentro del Resource | `AuthResource.java:42`; `LegacyTokenUtil.java:13`; `AuthResource.java:39` |
| A-03 | Campo `client` recibido y no usado | `LoginRequest.java:6` |

## Contexto

El servicio de autenticacion expone `POST /auth/login` y devuelve `token`, `expiresIn` y `user` (contrato en [docs/ENDPOINTS.md](docs/ENDPOINTS.md)).

El estado actual del token no es el descrito en la version previa de esta HU: no hay HMAC ni se lee `AUTH_TOKEN_SECRET`. El token es el Base64 de `username|role|exp|SECRET` (`LegacyTokenUtil.java:14-15`). Por eso no tiene firma, no tiene claims estándar y el secreto viaja dentro del propio token.

## Ajustes necesarios

- **H-02**: reemplazar el Base64 casero por un token firmado. Decision abierta: HMAC-SHA256 propio o libreria JWT (ver Decisiones abiertas).
- **H-02**: el token debe incluir los claims `sub`, `client`, `iat` y `exp`. El claim de rol que hoy viaja en el token debe conservarse o justificarse su retiro.
- **H-02**: validar firma y `exp` en un unico componente de seguridad, no en `AuthResource`.
- **H-04**: leer el secreto de la variable de entorno `AUTH_TOKEN_SECRET`, sin valor por defecto en el codigo. Para laboratorio local, el valor de prueba se documenta en el README y nunca en una clase Java. Quitar la constante de `LegacyTokenUtil.java:8`.
- **H-07**: mover la duracion del token a una constante con nombre. Esa misma constante alimenta `exp` y `expiresIn`, reemplazando el `3600` de `AuthResource.java:42` y `LegacyTokenUtil.java:13`.
- **H-07**: la creacion del token sale de `AuthResource` y pasa a un servicio, para que el Resource solo mapee HTTP.
- **A-03**: leer `client` de la solicitud, validarlo y reflejarlo en el claim `client` del token. Las reglas de validacion se definen en Decisiones abiertas.
- **H-02**: `expiresIn` debe coincidir con `exp - now` dentro de una tolerancia documentada.
- Mantener el contrato de `/auth/login` (campos `token`, `expiresIn`, `user`). Los cambios son internos.

## Decisiones abiertas

- HMAC propio frente a libreria JWT (decision tecnica de HU-01).
- Reglas de validacion del campo `client` (lista permitida, formato o ambas).
- Si el claim de rol se conserva en el token.
- Tolerancia en segundos para la coherencia entre `expiresIn` y `exp - now`.

## Criterios de aceptacion

| Id | Criterio | Prueba que lo verifica | Hallazgo |
|---|---|---|---|
| CA-01 | Un token valido contiene `sub`, `client`, `iat` y `exp`. | `TokenClaimsTest`: login valido, decodificar el token y comprobar que los cuatro claims existen y `exp > iat`. | H-02, A-03 |
| CA-02 | Un token con payload o firma alterados es rechazado. | `TokenSignatureTest`: alterar un byte del payload y de la firma; el validador debe rechazarlos. | H-02 |
| CA-03 | `expiresIn` coincide con `exp - now` dentro de la tolerancia definida. | `LoginExpiryTest`: diferencia entre `expiresIn` y `exp - now` menor o igual a la tolerancia. | H-02, H-07 |
| CA-04 | Un token con `exp` pasado es rechazado. | `TokenExpiryTest` con reloj inyectado: validar un token generado 1 segundo despues de `exp`. | H-02 |
| CA-05 | Login valido responde 200; credenciales invalidas responden 401. | `AuthResourceTest` (ya existe el caso valido) mas `LoginErrorsTest` con credenciales invalidas. | H-02 |
| CA-06 | El secreto se lee de `AUTH_TOKEN_SECRET`; sin la variable, el arranque falla en perfil `prod`. En tests se usa un valor aislado. | `SecretConfigTest`: sin variable, falla la inicializacion; con variable de prueba, el token se firma. | H-04 |
| CA-07 | El literal del secreto ya no aparece en `src/main`. | `SecretNotHardcodedTest`: busca en `src/main` el valor literal que hoy existe en `LegacyTokenUtil.java:8` y no lo encuentra. | H-04 |
| CA-08 | Ningun log contiene el token ni el secreto. | `TokenLogRedactionTest`: captura de logs durante un login valido; no debe aparecer el token ni el secreto. | HU original |
| CA-09 | La duracion del token viene de una constante con nombre y es la misma para `exp` y `expiresIn`. | `TokenTtlTest`: `expiresIn` y `exp - iat` igualan la constante. No hay literal `3600` en `AuthResource`. | H-07 |
| CA-10 | El valor de `client` de la solicitud se refleja en el claim `client`; un valor no permitido responde 400. | `ClientClaimTest`: `client` valido se refleja; `client` no permitido devuelve 400. | A-03 |
| CA-11 | El codigo nuevo o modificado tiene cobertura de 85% o mas. | Reporte JaCoCo generado en `verify` (`target/site/jacoco`). | REGLAS.md, meta 7 |

## Evidencia esperada

- Resultados de las pruebas `TokenClaimsTest`, `TokenSignatureTest`, `TokenExpiryTest`, `LoginExpiryTest`, `LoginErrorsTest`, `SecretConfigTest`, `SecretNotHardcodedTest`, `TokenLogRedactionTest`, `TokenTtlTest` y `ClientClaimTest`, en verde.
- Configuracion de `AUTH_TOKEN_SECRET` documentada en el README, con instrucciones de laboratorio y sin valor real.
- Reporte de cobertura JaCoCo con 85% o mas en el codigo modificado.
- Evidencia de logs redactados (salida de `TokenLogRedactionTest`).
- Contrato de `/auth/login` sin cambios (comparado contra [docs/ENDPOINTS.md](docs/ENDPOINTS.md)).
